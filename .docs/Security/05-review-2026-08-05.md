# Security — Full review, 5 August 2026

`Status: Accepted` · `Last updated: 2026-08-05` · Reviewed at `release/2026-08-05` (`@connected/types` 0.3.0)

A whole-repository pass rather than a diff review, run at the point where every functional
requirement was built or blocked. Scope: dependencies, secrets, transport and headers, session and
cookie handling, input validation, authorization coverage, rate limiting, log hygiene, injection
surface, and the static-analysis history.

**Three findings need action.** One is a real gap in the browser-facing app; one is a deployment
assumption that is unsafe if it turns out to be wrong; one is a dependency bump. Nothing found is
an exploitable authorization or data-exposure defect.

## Findings

### 1. The web app sets no security headers — **high**

`apps/web/next.config.*` defines no `headers()`. The API is behind `helmet()`; the app a browser
actually loads is not. So there is **no `Content-Security-Policy`, no `X-Frame-Options` /
`frame-ancestors`, no `Referrer-Policy`, and no `Permissions-Policy`.**

The consequence that matters is **clickjacking**, because of what the school portal can do in one
click: approve a member into a school, withdraw a notice from every family, and — since S6-6 —
remove somebody's content from the moderation queue. A framed portal plus a persuasive overlay is
the whole attack.

The absent CSP is the second half: it is defence-in-depth against an XSS this codebase has no
known instance of, and its absence means any future one would be unconstrained.

**Fix:** a `headers()` block in `next.config` with `frame-ancestors 'none'`, a CSP appropriate to
Next's inline-script requirements, `Referrer-Policy: strict-origin-when-cross-origin`, and
`Permissions-Policy` denying camera, microphone and geolocation.

### 2. `trust proxy` is unconditional — **medium**

`app.set('trust proxy', true)` (`apps/api/src/app.ts`) tells Express to trust every hop, so `req.ip`
becomes the **leftmost** value of a client-supplied `X-Forwarded-For`.

Behind an ingress that overwrites that header this is correct and intended. If the API is ever
reachable without one — a misconfigured service, a port exposed during an incident, a preview
environment — a caller can set the header themselves and choose their own apparent address.

Two limiters key on IP: `credentialLimiter` on login, registration and password reset, and the
`/rum` limiter. Both are evadable in that situation. The per-address login backoff (FR-AUTH-011) is
unaffected, because it keys on a hash of the email rather than the address, which is exactly why
that layer exists.

**Fix:** replace `true` with the number of proxies in front, or the ingress subnet. It is a
one-line change and it turns an assumption into a statement.

### 3. Five dependency advisories, all transitive through Next — **medium, not currently reachable**

| Severity    | Package   | Path                     |
| ----------- | --------- | ------------------------ |
| high        | `sharp`   | `next@16.2.12 > sharp`   |
| high ×2     | `postcss` | `next@16.2.12 > postcss` |
| moderate ×2 | `postcss` | `next@16.2.12 > postcss` |

The `postcss` advisories concern source-map handling of attacker-controlled CSS at build time. The
CSS built here is ours.

The `sharp` advisories are libvips CVEs reached through Next's image optimizer. **That path is not
reachable in this app:** `next/image` is used nowhere — every image site uses a plain `<img>` with a
signed URL, deliberately and with a comment saying why in four places — and no `images` config
exists, so remote optimization is refused by default.

**Fix:** bump Next 16.2.12 → 16.3.0 and re-audit. Reachability today does not make it acceptable
tomorrow; the next person to reach for `next/image` should not inherit this.

### 4. Alert #6 is open on `main` until the next release — **informational**

`js/biased-cryptographic-random` was fixed on `development` (#79) and closes when `main` is next
scanned. The finding itself is described in `01-authentication.md`.

### 5. `infrastructure/docker/` is empty — **informational**

`Deployment/00-environments.md` describes "multi-stage Docker images … minimal runtime base,
non-root user". The directory contains nothing. That is honest as a plan and misleading as a
status; container hardening is unbuilt and unreviewed.

### 6. Root-level `token` is not redacted — **low**

The pino redact list has `*.token`, which matches `foo.token` and not a root-level `token`. Nothing
currently logs one — the console mailer prints a reset token deliberately, and refuses to construct
itself in production for that reason — but adding the root path is free.

## What was checked and found sound

- **No secrets in the tree.** No `.env` tracked, no keys or certificates, no high-entropy literals
  in source or infrastructure. `.env` and `.env.*` are ignored.
- **Every write endpoint validates or takes no body.** The POSTs without `validateBody` are
  id-in-path actions (`follow`, `like`, `block`, mark-read) using `uuidParam`, plus `/rum`, which
  parses with zod inline, and the upload route, which is bounded by multer and magic-byte checks.
- **Cookies.** The API refresh cookie is `httpOnly`, `secure` outside development, `SameSite=Strict`
  and scoped to the refresh path. The web session cookies are `httpOnly` and `secure` in
  production.
- **CSRF.** `SameSite=Strict` plus an origin check on any write presenting the refresh cookie —
  covering the compromised-subdomain and non-enforcing-browser cases `SameSite` does not.
- **No unsafe SQL.** `$queryRawUnsafe` and `$executeRawUnsafe` appear only in Prisma's generated
  client and in the test-suite reset. Application queries are the typed client or tagged templates.
- **Passwords** are argon2id, never logged, never returned. Reset tokens, refresh tokens, recovery
  codes and 2FA challenges are all stored as SHA-256 digests; TOTP secrets are encrypted at rest.
- **Rate limiting** on auth, posting, messaging, realtime tickets and RUM, plus per-address login
  backoff.
- **Authorization** is asserted, not assumed: the permission-matrix suite exercises all seven roles
  against the live API for every capability in the product contract, and its unimplemented list is
  empty.

## Not in scope, and worth saying so

- **No penetration test.** This is a code and configuration review.
- **Container and Kubernetes hardening** could not be reviewed, because those files do not exist.
- **The moderation queue's privacy promise** ("nobody at your school is told") is enforced in the
  DTO and asserted, but has not been reviewed by anybody with a safeguarding background. That is a
  different kind of review from this one and it should happen before social reaches real children.
